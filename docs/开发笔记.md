# 开发笔记

## 一、技术选型：为什么是 Electron

**背景约束**：本机只有 JDK 1.8（现代 Java 桌面方案普遍要求 11+/17+，且无 Maven/Gradle 命令），已装 Node 22 + npm 10，未装 Rust。

| 方案 | 就绪成本 | 结论 |
|---|---|---|
| Electron + 原生 HTML/JS | 0（Node 已就绪） | **采用** |
| Electron + React + Vite | 中（多一层构建链路） | 工具数破 20 再考虑 |
| JavaFX / Compose Desktop | 高（先装 JDK 21 + Gradle，首次构建几百 MB） | 放弃 |
| Tauri | 高（Rust + MSVC 工具链） | 放弃 |

选 Electron 的真正理由不是"跨平台"，而是：

1. **工具集的共性是「表单 + 文本转换 + 即时反馈」**，这正是 Web 渲染层的强项。做 JSON 树形折叠、正则高亮、富文本预览时，Web 的能力是 Swing/JavaFX 的十倍量级。
2. **零构建**。没有打包器意味着：改一行 JS → 刷新窗口 → 立刻看到效果，且没有 sourcemap 错位、没有 HMR 状态丢失、没有构建配置腐烂。
3. **加工具的成本趋近于零**，且工具之间天然隔离（各自一个模块，互不影响）。

### 已知代价（心里有数就行）

- 空壳体积 130–180MB（捆绑 Chromium）
- 空载内存 100–200MB
- **重计算会卡 UI**：单线程 JS。将来若要处理 GB 级日志、批量图片，必须走 `Worker` 或原生模块，不要在渲染进程里直接 for 循环
- 原生观感需要自己补（菜单、窗口行为、字体）

如果哪天诉求变成"5MB 绿色版"或"处理几十 G 数据"，那是换 Tauri / 加原生模块的信号，不是在这套架构上硬撑。

## 二、几个关键实现决定

### 1. 用自定义协议 `app://`，不用 `file://`

`file://` 下 Chromium 会以 CORS 为由拦掉 ES Module 的 `import`，只能退回传统 script 或关掉 `webSecurity`（不安全）。

方案：主进程注册特权协议 `app://`，`protocol.handle` 把请求映射到 `src/renderer` 目录，窗口加载 `app://bundle/index.html`。代价是 15 行代码，收益是**原生 ESM + ES2022 语法 + fetch 可用**，且仍然零构建。

`resolveSafePath()` 里做了目录穿越防护，请求路径必须落在 renderer 目录内。

### 2. 安全模型：三件套全开

`contextIsolation: true` + `nodeIntegration: false` + `sandbox: true`。

渲染进程完全拿不到 `require` / `process`。所有系统能力必须经 `preload.js` 的 `contextBridge` 显式暴露，主进程侧再由 `ipc.js` 逐个 `ipcMain.handle`。这样任何第三方工具代码都无法偷偷读硬盘——**这是给自己留的安全底线，不是形式主义**。

### 3. 工具契约：一个对象，一个 mount 函数

```js
{ id, name, desc, icon, group, keywords, mount({ root, api, actions }) → cleanup? }
```

- 不用类、不用继承、不用生命周期钩子满天飞。一个 `mount` 足够覆盖工具"输入 → 转换 → 输出"的全部形态。
- `mount` 返回清理函数用于清定时器 / 移除全局监听（见 `timestamp` 工具的 1 秒刷新）。
- `registry.js` 在启动时 `validateTools()`，id 重复或字段缺失直接抛错——早失败比点了侧边栏白屏好。

### 4. 无框架的 DOM

`core/dom.js` 的 `h()` 约 40 行，覆盖了 95% 的构建需求。**如果将来某个工具复杂到 `h()` 写不动了，先考虑把那个工具单独升级（比如局部引 React），而不是把整个外壳框架化**——外壳一旦引入构建步骤，加工具的心智成本就再也回不去了。

## 三、文件列比对：为什么逻辑放在主进程

三个关键决定：

### 1. 读取放在主进程，流式，不走 IPC 传大字符串

如果在渲染进程里做，就得先 `api.readText()` 把整个文件变成字符串再 `split('\n')` —— 大文件会直接卡死界面，还会因为 IPC 序列化把内存翻倍。

所以新增 `src/main/column-scan.js`：`createReadStream` + `TextDecoder(stream: true)` 逐块解码、手工切行，只在内存里留一个 `Map<值, true>`。渲染进程拿到的只是唯一值数组。

### 2. 编码必须可选，默认 UTF-8，可切 GBK/GB18030

中文 Windows 上大量历史数据是 GBK 编码，Node 默认按 UTF-8 解码，遇到 GBK 文件会得到乱码 —— 这不是理论问题，院端导出的 txt 大概率是 GBK。

实现上：`encoding` 参数经 `ENCODING_ALIASES` 映射到 WHATWG 编码名（`gbk` → `gb18030`，用超集解码更稳），交给 `TextDecoder` 处理。测试里专门有一条用例验证「用错编码确实会乱码」，证明这个选项不是摆设。

### 3. 列序号在界面上从 1 开始

0 基列号直接暴露给用户很反直觉（尤其对非程序员）。界面收 1 基、内部减 1，提示文案里写明对应关系。

### 4. 结果展示有上限，但复制/导出是全集

列表默认只渲染 **100 行** DOM（几千个节点切标签页会明显卡顿），面板上「展示行数」可改，上限 2000；超出时给一行提示说明「复制与导出包含全部数据」。**这是有意的取舍，不是 bug。**

展示行数只影响列表渲染，所以改它不重新扫描、也不重算统计，只调 `refreshList()` 重建列表——不能走 `renderResult()`，那会把筛选框和标签页一起重建，输入焦点会丢。

### 5. 双数据源：每一侧独立选「文件」或「粘贴」

真实用法不只是「两个文件对比」，更常见的是一边是导出的文件、另一边是从系统里复制出来的一段。所以槽位做成独立的模式切换，A 用文件、B 用粘贴是完全合法的组合。

关键约束：**两条路径必须共用同一份解析实现**，否则「文件里算出来 5 个唯一值，粘贴同样的内容算出 4 个」这种 bug 极难发现。

做法：`column-scan.js` 抽出 `createCollector({delimiter, columnIndex, trim})`，逐行喂入并累计。`scanColumn()` 走流式解码后喂它，`scanColumnFromText()` 直接 split 后喂它。测试里有一条专门的断言：**同一份内容分别走两条路径，结果必须完全一致**。

### 6. 实时比对的两个坑

**防抖 320ms**：粘贴大段文本时每次按键都算一遍会卡。但只防抖不够 ——

**竞态**：用户改了列号，第一次请求还在读文件，第二次请求已经发出。如果第一次的结果后到，会把界面覆盖成旧数据。用一个自增的 `runSeq` 解决：每次 `run()` 开头取号，await 回来后比对号是否还是最新，不是就丢弃。

**不要把「重算」和「重渲染」混在一起**：切标签页只重渲染列表，不重新扫描文件。粘贴模式下刷新槽位脚注时也不能重建整个槽位 DOM —— `body.append(textarea)` 会移动已聚焦的 textarea，导致光标跳走。所以槽位拆成 `renderBody()`（模式/文件变化时重建）和 `updateFoot()`（只改文字）两个粒度。

### 7. 一个 CSS 作用域踩坑

`.split .textarea { flex: 1; min-height: 180px }` 本意是给 JSON/Base64 的双栏编辑区用，结果也命中了槽位里的粘贴框，把它撑成 180px 高、整页被顶长。

修法是把选择器收窄成 `.split .field .textarea` —— 槽位里的 textarea 不在 `.field` 内，自然不受影响。**教训：通用布局类一旦和具体结构耦合，迟早会误伤别处；选择器宁窄勿宽。**

## 四、SQL IN 生成器：把规则从界面里拆出来

这个工具没有系统调用、没有文件读写，纯文本变换，所以逻辑全部留在渲染进程，新增的 IPC 只有一个（`readText` 支持指定编码）。

### 1. `parse.js` 单独成层

界面代码（`index.js`）只做控件和状态，切分/清洗/拼装全部在 `parse.js`，**它不 import 任何 DOM 相关的东西**。理由：这块规则最多、最容易出错，而且全是纯函数，能脱离界面断言。

代价是它是 ESM 模块，Node 里 `require` 不了（项目没有 `type: module`），所以测试走的是「注入页面 + 动态执行」这条既有链路，没有为它单独引入构建或测试框架。

### 2. 四条必须做对的规则

- **引号内的分隔符不切分**。`'A,B'` 是一个值。直接 `split(',')` 会把用户数据劈开，而且这种错很难当场发现。
- **值两端的引号要先剥掉**。已经带引号的 `'DIP001'` 直接拼会变成 `''DIP001''`，SQL 语法错误。
- **数字与 `null` 不加引号**。`1e3`、`-4.5` 都算数字；`null` 输出 `NULL`。否则 `IN ('1')` 在数值列上会带来隐式转换和索引失效。
- **BOM 必须剥掉**。UTF-8 文件开头的 BOM 会粘在第一个值上，生成的 IN 列表里第一个值永远匹配不到，而且肉眼看不出来。所以 `readText` 里统一 `replace(/^\uFEFF/, '')`。

### 3. 一个被测试抓到的真实 bug：方向开关互相覆盖

最初的设计是「输入里出现 `NOT IN` 就自动把方向切过去」。实现成每次 `transform()` 都检查，结果用户手动点回 `IN` 时，下一次渲染又把方向改回 `NOT IN` —— 开关看起来失灵。

修法：只在**输入内容变化时**才从数据里推断方向（记住上一次同步时的文本），选项变化不触发推断。端到端测试里那条「手动切回 IN」就是专门盯这个回归的。

**教训：凡是「从数据推断出来的状态」和「用户手动设置的状态」共用一个变量，就必须明确谁优先、什么时候重新推断，否则一定互相打架。**

### 4. 四种输出模式的取舍

| 模式 | 输出 | 用途 |
|---|---|---|
| `IN 单行` | `id IN ('a', 'b')` | 直接贴进 where 条件 |
| `IN 多行` | 带缩进的块 | 值多时好读、好 diff |
| `值列表` | 每行 `'a',` | 粘进已有的 `IN (...)` 里补齐 |
| `纯数据列` | 每行一个原始值 | 反过来把 IN 列表还原成一列数据 |

`值列表` 的每行都带尾逗号（包括最后一行），因为它的用途就是往已有列表里追加；要干净结果用 `纯数据列`。

### 5. 分片是为了绕开数据库上限

Oracle 的 `IN` 列表硬上限 1000 项，超了直接报错。所以加了「每 N 个值分片」，输出成多段用 `OR ... IN (...)` 连接（`NOT IN` 时自动换成 `AND`，否则语义会反）。默认 0 = 不分片，不干扰日常使用。

## 五、测试策略

- **逻辑层**（`npm test`）：不依赖 Electron，纯 Node 跑 `column-scan.js`。文件读写的边界条件太多（CRLF、BOM、空行、超长行、越界列），必须自动化，靠手动点界面是测不全的。
- **交互层**（`npm run test:e2e`）：真实窗口 + 注入脚本 + 预设文件路径，断言渲染出的数字。能跑出截图，改完样式能立刻目视检查。不带场景参数时依次跑 `test/e2e/` 下所有脚本；场景需要样例文件就建 `test/fixtures/<场景名>/`，里面的文件按文件名顺序进 `SMOKE_FIXTURE_QUEUE`。
- 三个测试钩子（`SMOKE_SCRIPT` / `SMOKE_SHOT` / `SMOKE_FIXTURE_QUEUE`）都只在 `--smoke` 下生效，正常启动零影响。

## 六、打包（electron-builder + NSIS）

### 1. asar 里 `app://` 能不能读？——实测能，但必须验证

这是打包前最大的未知数：`protocol.handle` 里用 `net.fetch(pathToFileURL(target))`，而这些文件打包后会躺在 `app.asar` 里。`fs` 有 Electron 的 asar 补丁，但 `net.fetch` 走的是 Chromium 一侧的 file 加载器，理论上可能不认 asar 虚拟路径。

结论：**Electron 45 实测可用**，不需要把 renderer 挪到 asar 外、也不需要改写成 `fs.readFile` + 手搓 `Response`。

验证方式不是看构建日志，而是让**打包后的产物自己跑冒烟**：

```bash
SMOKE_HASH="sql-in" SMOKE_SHOT="dist/check.png" "dist/win-unpacked/工具集.exe" --smoke
```

输出 `[renderer] app-ready tools=5` 且截图有内容，才算真能跑。**这也是保持冒烟钩子留在生产代码里的价值**——它让"产物可用"变成一条可执行的断言，而不是靠人双击试。

### 2. 图标：没有 Pillow 也能出 ico

`build/make-icon.py` 只用 `zlib` + `struct` 手写 PNG，再按 ICO 格式把 7 个尺寸（16~256）作为 PNG 条目封进去。Vista 以后的 Windows 和 electron-builder 都接受 PNG-in-ICO。

图案是圆角渐变底板 + 三条白色横条，配色取侧边栏 `brand-mark` 的 `#4D7BFB → #2F4FCB`，这样任务栏图标和界面里是同一套色。抗锯齿用 3×3 子采样算覆盖率，不依赖任何图形库。

**坑**：第一版把矩形的 `(x0, y0, x1, y1)` 参数顺序写错了，`y0 > y1` 导致覆盖率恒为 0，导出一张全透明图。视觉验证要导出 256 那张 PNG 直接看，别只看"文件生成了、体积正常"——透明 PNG 压缩后只有几百字节，尺寸检查发现不了。

### 3. 体积与体积的去处

| 项目 | 0.2.0 初版 | 优化后 |
|---|---|---|
| 安装包 | 116MB | 98MB |
| 安装后 | 358MB | 310MB |
| app.asar 内应用代码 | ~100KB（32 个文件） | 不变 |

三件有效的事：`compression: "maximum"`（NSIS 走 LZMA 最大压缩）、`afterPack` 钩子删语言包（55 → 2 个，只留 zh-CN / en-US）、`differentialPackage: false`（不做自动更新就不需要差量数据）。即便如此 95% 仍是 Electron 运行时，**exe 本体 239MB**，要数量级下降只能换 Tauri（需 Rust 工具链，见第一节）。

**坑：不要用 `electronLanguages` 配置删语言包**——它在 unpack 阶段用 Node fs 逐个删 pak，会被本机的批量删除保护拦截，构建中途终止且产物残缺。`scripts/prune-locales.js` 用 cmd 子进程删除，绕开 Node fs 层（该脚本只在打包机上跑，不进 asar）。

### 4. 两个环境坑

- **批量删除保护**：这里的执行环境会拦截一次性删除超过 50 个文件的操作，而 electron-builder 每次打包都要先清空 `win-unpacked`（74 个文件），于是直接报 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`。解法是打包前先手动 `rm -rf dist`。
- **镜像**：`electron-builder` 除了 electron 本体，还要下 `nsis`、`nsis-resources`、`7zip-win-x64`。只设 `ELECTRON_MIRROR` 不够，必须同时设 `ELECTRON_BUILDER_BINARIES_MIRROR`，否则卡在下载。

### 5. 没做的两件事

- **代码签名**：没买证书，`signing is skipped`，Windows 首启会提示「未知发布者」。自己用无所谓；要分发就得签名，否则用户会被 SmartScreen 劝退。
- **自动更新**：`electron-updater` 需要发布服务器（GitHub Releases 或自建），等真有分发需求再上。

## 七、常驻与状态记忆（0.2.0）

### 1. 全局快捷键 + 托盘：从「一个程序」变成「随手的工具」

工具箱的价值和唤出成本成反比。开开始菜单 → 找图标 → 等窗口 → 找功能，四步走完人就烦了。所以这一版把唤出压缩成一步：`Ctrl+Shift+Space` 唤出并聚焦搜索框，打字回车直达工具；再按一下收起（判断的是「可见且有焦点」，避免来回切应用时按一下没反应）。

两个防御性设计：

- **快捷键注册失败不静默**。全球范围内 `Ctrl+Shift+Space` 被输入法或其他工具占用的概率不低，注册失败时在托盘菜单里写明「被占用，已停用」。
- **Alt+Space 是 Windows 系统菜单**，F 区功能键常被输入法占用，选键时都避开。

### 2. 关闭按钮 = 藏进托盘，但给用户留退路

默认 `close` 事件被拦截改为 `hide()`，这是工具类软件的常见预期（Xinpinyin、Snipaste、uTools 都这样）。但「点 X 结果进程还在」对另一部分人是惊吓，所以托盘菜单放了「关闭窗口时最小化到托盘」的勾选项，两种习惯都能满足。托盘左键固定为唤出而非切换——「点了没反应」比「多按一次」更伤体验。

### 3. 单实例锁

`app.requestSingleInstanceLock()`。重复启动的第二进程立即退出，由既有实例 `showWindow()`。没有这个锁，双击两次快捷方式就是两个托盘图标 + 两个进程抢一个 settings 文件。

### 4. store.js：为什么手写而不用 electron-store

需求只是「读一次、改很多次、落盘一次」。手写一百行换来行为完全可见：深合并语义（对象逐键合并、数组标量替换）是工具配置局部更新的基础；写入走「临时文件 + rename」，同一分区上 rename 是原子的，不会出现断电后半截 JSON。文件损坏时不覆盖，rename 成 `.corrupt-<时间戳>` 留证。

**冒烟模式用独立的 userData**（`os.tmpdir()/use-tools-smoke`，每次运行清空，`SMOKE_KEEP_STATE=1` 可保留）。这一步很关键：否则测试会把 `lastRoute`、主题写进真实设置，反过来上一次测试的状态又会污染下一次截图。

### 5. 主题：渲染进程零逻辑

浅色令牌在 `:root`，暗色整组写在 `@media (prefers-color-scheme: dark)` 里。渲染进程切主题只是调 `nativeTheme.themeSource`，Chromium 会自动更新媒体查询——**没有任何手动刷新或双套 class 的逻辑**。配套纪律：组件样式不允许写死颜色（`btn-primary` 白字这类主题不变量除外），这一版把 app.css 里 6 处散色全部收编成令牌。

`backgroundColor` 也跟着 `nativeTheme` 走，否则暗色下启动瞬间会闪一下白底。

### 6. 状态记忆的边界

- **记什么**：窗口几何、lastRoute、主题、两个高频工具的选项。列比对**不记数据**（粘贴内容本质是临时物，文件可能被移动）；SQL IN **连输入一起记**（上限 20KB，超过只记选项）——它的典型用法是「昨天粘了一列 ID 今天接着整理」，数据丢了比选项丢了恼火。
- **恢复让位于用户**：恢复是异步的（IPC 往返），用户可能恢复落地前就动手了。用一个 `touched` 标记守卫——它恰好等于「persistState 被调用过」，因为 persistState 只会被用户操作触发，不需要单独维护第二个状态。

### 7. 托盘图标的 16px 是独立渲染的，不是缩放

256px 图标缩到 16px 后，三条横条（间距 0.155×高度 ≈ 2.5px）糊成一块白斑，目视检查才看出来。托盘版单独给了几何参数：间距拉开到 0.22、线宽收窄。教训还是那条：**小尺寸图必须按小尺寸重新设计，并且要放大看**。

## 十、Tauri 外壳

**动机**：Electron 97.9MB 的安装包里，约 239MB（解包后）是 Chromium 主程序的固定成本，语言包裁剪 + 最大压缩已经压到极限。Tauri 复用系统 WebView2，同一份渲染层直接跑。

**关键决定**

1. **前端零改动**：新增 `core/bridge.js`，检测到 `window.__TAURI__` 时用 `__TAURI__.core.invoke` 还原一份**同签名**的 `window.api`（连 `onSummoned` 的退订函数都保留了）。在 `index.html` 里放在 `app.js` 之前——同为 module，执行顺序有保证。Electron 下它什么都不做。
2. **能力全走自定义命令**：插件只在 Rust 侧用（dialog / clipboard / global-shortcut / single-instance），JS 端不碰插件 API。于是 `capabilities/default.json` 只开 `core:default` + `core:event:default`，权限面降到最小。
3. **命令参数一律用单结构体**（`args` / `options` + `serde(rename_all = "camelCase")`），不依赖 Tauri 对 camelCase↔snake_case 的参数名推断，读代码时也不用交叉对照。
4. **不配 devUrl，直接把 `../src/renderer` 当 frontendDist**：Tauri 用内部资源协议提供文件，ESM 的 import 能正常工作——这正是原来自定义 `app://` 协议存在的理由，现在交给框架了，也不需要任何打包器。
5. **数据目录独立**：用 `app_config_dir()`，实际是 `%APPDATA%\com.usertools.desktop`，与 Electron 版的 `%APPDATA%\工具集` 互不干扰，两版可以同时装着。
6. **列扫描**：`encoding_rs_io::DecodeReaderBytes` 包一层流式解码器 + `read_until(b'\n')` 逐行喂 collector，与 JS 版的 `TextDecoder({stream:true})` 语义一致（GBK 仍映射到 GB18030 超集）。

**踩坑**

- `tauri.conf.json` 的窗口配置**不接受 `spellcheck` 字段**（老模板遗留），报错发生在 build script，看着像版本不匹配，其实是配置多了一个键。
- `WebviewWindow` 上没有 `webview_version()`，要用自由函数 `tauri::webview_version()`。
- `on_window_event` 回调给的是 `&Window` 而不是 `&WebviewWindow`，存窗口几何的函数签名要对齐它。
- Rust 里 `"a||1".split(&['|','|'])` 等价于「按任意一个 `|` 切」，多字符分隔符必须存 `String` 再用 `&str` 切。这个 bug 是单测抓到的（JS 版没有对应问题，因为 `String.split(str)` 本来就是整体匹配）。
- **别指望用 `document.title` 回传断言结果**：WRY 不会把 `document.title` 同步到窗口标题，`Window::title()` 永远返回配置里的标题。自检改成注入 JS 直接 `invoke('smoke_report', …)`，顺带把 invoke 通道也验了。
- NSIS 打包要从 GitHub 下载工具链，国内直连被掐（`peer closed connection` / 代理 502）。**预铺 `%LOCALAPPDATA%\tauri\NSIS` 会被完整性检查打回**——它除了 `NSISBin/makensis.exe`、`Stubs/lzma-x86-unicode`，还要一个编译进 CLI 的 `Plugins/x86-unicode/additional/nsis_tauri_utils.dll`，手工拼不出来。exe 本身不需要 NSIS，开代理再打安装包即可。

**验证**：`cargo test` 3 条（列扫描语义）+ 自检冒烟 4 阶段（外壳与侧边栏 / 工具页挂载 / invoke 往返 / 列扫描结果），debug 与 release 两种产物都全过（`USE_TOOLS_SMOKE=1`），退出码 0。

## 十一、视觉与排版（0.2.x）

### 1. 字体栈
- 正文：`Noto Sans SC` → `Segoe UI Variable Text` → `Microsoft YaHei UI` → …
  中文优先用系统已装的 `C:/Windows/Fonts/NotoSansSC-VF.ttf`（可变字重，`650`/`600` 是真实字重，不再是拿 Bold 硬凑的假粗）。缺了会自动回退雅黑 UI，不会崩。
- 等宽：`Cascadia Mono` → `Cascadia Code` → `Consolas` → `Noto Sans SC` → `monospace`。
  中间留 Noto 是刻意的：代码区里的中文若一路回退到 `monospace`，会掉到系统的宋体，和周围界面完全脱节。
- `-webkit-font-smoothing: auto`：Windows 上走次像素渲染；`antialiased` 会让 14–15px 的中文笔画发虚。
- `font-variant-numeric: tabular-nums`：数字等宽，统计值刷新时不左右跳。
- 不打包字体：CJK 子集约 1–2MB，对 3.8MB 的包不划算，且子集外的生僻字回退会造成字形混排。

### 2. 字号（2026-11 定稿）
正文 14.5px ｜ 顶栏标题 18px ｜ 按钮 32px 高 / 13.5px 字 ｜ 输入框 34px ｜ 文本域 13px ｜ 说明 12.5px ｜ 统计数字 20px ｜ 侧边栏 246px。

### 3. 三条容易踩的排版规矩
- **选中态不许改字重**：`.seg` / `.tab` 的 `.is-on` 一旦加 `font-weight: 600`，按钮变宽会把整条分段控件的边框撑缩（IN ↔ NOT IN 实测差 3px 左右，看起来像“边框在收缩”）。改用底色 + 描边 + 强调色文字表达选中，并给按钮补 `border: 1px solid transparent` 保证宽度恒定。
- **不许出现横向滚动条**：`.tool-view` 用 `overflow-x: hidden` + `scrollbar-gutter: stable`；`.data-list` 的行改 `white-space: pre-wrap` 换行显示长值，别指望横向滚动——横条会占掉 11px 高度，卡片会跟着“收缩”一下。
- **顶栏与内容同宽**：`.topbar-inner` 与 `.tool-body` 共用 `max-width: 1320px` + `margin-inline: auto`；顶栏右 padding 取 37px（26 + 11）抵消 `.tool-view` 的滚动条槽位，否则两者居中线会差 5.5px。

### 4. 界面骨架统一（`core/ui.js`）
五个工具共用同一套骨架，改样式只改一处：

```
toolbar(左：模式与参数 , 右：内容快捷操作)
内容区（.split 文本域 / .input-grid 单行输入 / 文件槽位）
status
hint（一句话）
```

- **按钮分区**：文件类（导入 / 保存 / 导出）进 topbar actions；内容级（示例 / 清空 / 反向转换 / 重跑）进工具栏右侧；模式与开关（分段控件、键排序、实时刷新）进工具栏左侧。
- **输出区**：标签行右侧统一 `meta + 复制`，用 `field(label, control, tools)` 生成。
- **分段控件**：只允许用 `seg(options, current, onPick)`，选项带 `hint` 会变成 `title`。手抄一份 `<div class="seg">` 是之前样式漂移的根源（三处实现各自为政）。
- **状态行**：`statusBar()` 返回 `{ el, set(kind, text) }`，kind 传 `'' | 'ok' | 'err'`（列比对还用了 `busy`）。
- **复制反馈**：`copyButton(getText, write)`，1.2 秒后复原文案，别再各自写 `setTimeout`。

改完跑 `npm run test:e2e`——三个场景共 55 条断言会顺带验一遍挂载与交互。

### 5. 设置页（`#/settings`）
侧边栏左下角「设置」进入，不是工具，由 `app.js` 直接挂载 `settings.js`。

- **读写走哪**：关闭行为 / 主题 / 快捷键都存在 `settings.json` 的 `ui` 里。关闭行为是「读时才判断」（Electron 在 `win.on('close')`、Tauri 在 `CloseRequested`），所以设置页改完立刻生效，不需要重启。
- **快捷键是可变的**：`ui.hotkey` 存 accelerator 字符串（`Ctrl+Shift+Space`）。Electron 用 `globalShortcut.register`，Tauri 用 `global_hotkey` 的 `Shortcut::from_str` —— 两边都认这个写法，所以一份字符串够用。
- **改失败必须回滚**：先注销旧的再注册新的，新的失败就把旧的注册回去，并把错误显示在设置页。否则用户改到一个被占用的组合，会「连唤出都没了」。
- **按键录制**：`acceleratorFromEvent()` 只认 Ctrl/Alt/Shift/Super + 字母/数字/F1–F12/空格；不带修饰键的裸字母直接拒绝（否则会把正常打字全抢走），功能键允许单独使用。
- **冒烟环境**：Electron 的 smoke 模式不创建托盘，`app:hotkey.get` 返回 `available: false`，设置页显示「当前环境未启用」并禁用修改按钮——不要让测试环境假装快捷键生效。
- **托盘与设置页同步**：托盘菜单勾选「最小化到托盘」会写设置并广播 `settings:changed`，设置页收到后重新读一遍；反向则通过 `settings:update` 后重建托盘菜单。

## 十二、窗口尺寸与图标

### 1. 首次启动的窗口多大
默认 **1120×720 逻辑像素**（`tauri.conf.json` / `BrowserWindow` 的默认值）。这个数不是拍的：一般 1080p + 150% 缩放的桌面逻辑尺寸约 1707×960，1120 宽只占 66%，不至于一开就压满屏。

三条容易踩的规矩：
- **`settings.json` 里的 `window.width/height` 默认必须是 `null`。** 给了 1200×780 这种默认值会盖掉配置文件里的逻辑尺寸；「没有记录就不调 `set_size`」才是对的。
- **存内框、不存外框（2026-11 修）。** 记录的是**物理像素的内容区**（`inner_size()`），正好对上 `set_size()` 的语义。早前存的是 `outer_size()`（内容区 + 标题栏 + 边框），还原时被当成内容区用，于是每启动一次窗口就长大一圈（150% 缩放下 22×56 物理像素）——表现为「最大化再还原之后，界面大小不对」。
- **还原时按「可用区域」夹一次。** 换显示器或分辨率变小后，旧尺寸可能比屏幕还大；`restore_window_bounds` 超过 `work_area` 就收到 95%，位置落在所有屏幕外时干脆不还原（让窗口居中）。Electron 侧同样用 `workAreaSize` 夹一次。
- **别用节流存几何。** 拖拽和最大化动画每帧都发 `Resized`，节流会把「最后一个正确值」丢掉，留下一个动画中间值——最大化后点还原，存的可能就是整屏尺寸。现在改成：事件只投信号，后台线程等安静 320ms 再读当前几何落盘（`spawn_bounds_saver` / `persist_window_bounds`），并且最大化时只写 `maximized: true`、不动 `width/height`。

### 2. 图标为什么要分尺寸画
`build/make-icon.py` 纯标准库手绘（不装 Pillow），但同一套字形缩到 16px 会糊成一团白斑。所以按尺寸切换策略：

| 尺寸 | 处理 |
|---|---|
| 16 / 20 | 只画 **2 条**横条（3 条挤不出空隙），直角端点 |
| 24 / 28 | 3 条，3px 厚，端点吸附整像素 |
| 32 / 40 / 48 | 3 条，4–5px 厚，端点带圆角，仍按整像素对齐 |
| ≥ 64 | 按比例渲染，圆角端点 |

超采样分级：≤48px 用 8×8、≤128 用 4×4、更大的用 3×3——512px 也做 8×8 只会白等。ICO 里额外放了 **40 / 96** 两档，正好对上 Windows 的 125% / 150% 任务栏缩放，避免系统拿 32px 硬拉。

改完图标记得**重新编译**（图标是编译进 exe 资源的，替换 png 不重编没用）。

### 2. 三个坑（都是这次实际踩到的）

- **`git push` 报 `SSL certificate problem: unable to get local issuer certificate`**
  `D:\Git` 的 system 配置用 `sslBackend = openssl` + 自带 ca-bundle，本机证书链下校验失败。
  解法：仓库内 `git config http.sslBackend schannel`，改用 Windows 证书库；写在 `.git/config` 里，不影响其他仓库。

- **`gh` 参数里的中文会存成乱码**
  脚本语言把参数转成 ANSI（CP936）再交给原生程序，`gh repo create --description "中文"` / `gh release create --notes` 到 GitHub 上就变成「妗岄潰宸ュ叿闆嗭細…」。
  **中文不要走命令行参数**：直接调 REST API，请求体 `Content-Type: application/json; charset=utf-8`。

- **读回来的中文也会坏**
  `gh api ... | Out-File` 会先按控制台编码解码再重新编码，中文必坏。要原样落盘就让脚本直接写字节到文件，不要经过管道。

### 3. 附带一条环境坑

脚本里用 urllib 时会被 `HTTP(S)_PROXY` 环境变量劫持：本机那个代理不放行 github.com，而直连是通的。
解法：`urllib.request.build_opener(urllib.request.ProxyHandler({}))` 显式禁用代理。

顺带修正一个认知：**命令行工具的网络和图形界面/系统进程不一定同一条路**。这次 Bash 侧访问 github.com 全部超时，而系统里的 PowerShell 访问同一个地址返回 200——排查网络问题时要先确认「是谁在发请求」。

## 十四、列比对读表格与编码策略

### 1. xlsx 为什么不用「转 CSV」

直接读单元格更准：CSV 导出会丢前导零、把长数字变科学计数法、把日期变序列号，还要再猜一次编码。所以列比对按扩展名分流：

| 扩展名 | 读取方式 |
|---|---|
| `.xlsx` / `.xlsm` | 按单元格读（Rust 用 `calamine`，Electron 自己解 zip + XML） |
| `.xls` | **明确拒绝**，提示另存为 `.xlsx`（二进制 BIFF，两边解析成本都高，收益低） |
| 其它 | 原来的流式文本路径 |

表格语义（两条实现必须一致，否则同一份文件在两个外壳里结果不同）：

- 只读**第一个工作表**，第 N 列就是 Excel 里的第 N 列（1 基展示、0 基内部）
- **整行为空** → 计入空行（不参与去重）
- 目标列**没有值** → 计入「列数不足」，与文本路径的短行同义
- 数字去掉 `.0`（`1001.0` → `1001`）；布尔转 `TRUE/FALSE`；错误单元格（`#DIV/0!`）与空单元格一样跳过
- 分隔符与编码对表格**不生效**，界面上文件行会标注「表格 · 大小 · N 行」

Rust 与 Node 各有一份实现，靠**同一份 fixture** 对齐：`test/fixtures/compare.xlsx` 同时喂给 `cargo test` 和 `npm test`，断言值与行数完全一致。改任一实现都要两份测试一起跑。

### 2. 编码：默认「自动」，别逼用户猜

中文 Windows 上「ANSI」就是 CP936（GBK），Excel 导出的 CSV 绝大多数是它；而新建的文本文件多是 UTF-8。让用户在两个选项里二选一，猜错就是一片乱码。

现在的规则：

1. 有 BOM 按 BOM
2. 前 64KB 能按 UTF-8 **严格**解开 → UTF-8
3. 否则 → GB18030（GBK 的超集）

两个实现细节：
- 嗅探只读前 64KB，读完要 `seek(0)` 再交给流式解码器，否则开头那段会被跳过
- 判断 UTF-8 时必须容忍**末尾被截断的多字节字符**（样本边界正好切在汉字中间）：Rust 用 `err.error_len().is_none()`，JS 用 `TextDecoder.decode(sample, { stream: true })`

UI 上第三个选项直接叫 **ANSI**（内部 id 仍是 `gbk`，映射到 GB18030 解码），和记事本、Excel 的说法对齐；「自动」是默认值。

## 十五、切换工具为什么不销毁

每次切菜单都 `unmount` + 重新 `mount`，等于把用户刚粘进去的一屏数据扔掉。现在的做法是**挂载后常驻**：

```
mountTool(tool)
  ├─ 已挂过 → 把缓存的 root / 顶栏按钮接回文档，恢复 scrollTop
  └─ 没挂过 → 建 root，调用 tool.mount，存进 mountedTools
detachCurrent()   // 切换时只做这件事：节点从文档摘下，不调 cleanup
```

三个必须注意的点：

1. **顶栏按钮要跟着走**：`actions` 是共享的 `#tool-actions`，工具自己 append 的按钮在切换时必须先摘下（`entry.actionNodes`），否则下一个工具会看到上一个的按钮。没有加包裹元素，避免破坏 `.topbar-actions` 的 flex gap。
2. **摘下的节点不能留在文档里**：一旦留在文档里（哪怕 `display:none`），`document.querySelector` 仍会命中它，测试和工具内部的全局选择器都会串台。所以用 `node.remove()` 真摘，`mountedTools` 里只留引用。
3. **滚动位置按工具各存一份**：真正的滚动容器是 `#tool-view`，切换时记 `scrollTop`，回来再写回；否则会沿用上一个工具的滚动偏移。

设置页是例外——它不是工具，每次进入重新 `mount`，离开时调它自己的 cleanup（`closeSettings()`），因为那页没有任何需要保留的用户数据。

代价：所有打开过的工具都会常驻内存（5 个工具，可忽略），且 `cleanup` 在进程退出前不会执行；工具的清理函数只移事件监听、不做持久化，所以不影响任何数据。

## 十六、选项行怎么换行

选项面板的每一行是「若干个条件」，比如 `值引号 [单/双/不加] ｜ 值排序 [原序/升序/降序]`。窗口一窄，最容易出的问题是**标签留在上一行、它的控件被挤到下一行**，看上去像两个不相干的设置。

规则：**宽度够就并排，不够就整组换行**。实现只有两层：

```
.opt-row   { display:flex; flex-wrap:wrap; gap:8px }      /* 组与组之间可以换行 */
.opt-item  { display:flex; flex-wrap:nowrap; max-width:100% }  /* 组内永不拆开 */
.opt-label { flex:none; width:64px }
```

配套的三条约束，缺一条就会露馅：

- `.seg`（分段控件）要有 `flex-wrap: wrap` + `max-width: 100%`：单个组即使独占一行也可能比一行还宽（7 个选项），这时让**按钮整颗**换行，而不是把「制表符」三个字劈开。
- `.seg button` 与 `.check-label` 都要 `white-space: nowrap; flex: none`。之前「数字不加引号」在 520px 宽时被折成「数字不加引 / 号」，就是漏了这条。
- 一行里不止一个设置时，**每个设置必须各自成组**（`.opt-item`），不能把勾选项塞进相邻控件的组里——否则它会被迫跟着一起挤压，而不是自己换行。

一个例外要记着：**行尾的按钮不要用 `.spacer` 顶**。`.spacer` 是 `flex:1`，一旦换行它自己留在上一行、按钮孤零零掉到下一行左侧。改用 `margin-left:auto`，换行后按钮仍靠右。

真实最小窗口（940 逻辑像素、侧栏 246）下面板约 640px，此时 SQL IN 的四行都还是单行；520px 时才开始整组换行，460px 时「切分方式」的 7 个按钮会内部折成两行——都算预期。

## 十七、长文件名与紧凑行高

### 1. 文件名省略号光有 `text-overflow` 不够

`.file-name` 一开始就写了 `overflow:hidden; text-overflow:ellipsis; white-space:nowrap`，但实测 66 字符的文件名照样把槽位撑到 **830px**（槽位只有 759px），按钮被挤出可视区后被 `overflow-x:hidden` 直接裁掉——因为**这两层容器没有收缩**：

```
.file-slot       { min-width: 0 }   ← 网格项默认 min-width:auto，会被内容撑宽
.file-slot-main  { flex: 1 1 auto; min-width: 0 }  ← 原来只有内联 minWidth:0，没有 flex
```

补上之后 `scrollWidth(830) > clientWidth(239)`，省略号才真正出现。判断有没有生效不要看有没有 `…`，要看 `scrollWidth > clientWidth`。

### 2. 行高与说明文字

- 结果列表行：`padding: 4px → 3px → 2px`、`line-height: 1.5`，行高降到 **约 24.5px**，一屏能多看到两三行。
- 底部说明压到一行（48 字）：`改动即时重算；表格按单元格读，忽略分隔符与编码；编码「自动」优先 UTF-8，否则按 ANSI。`
  原来 61 字，在 700px 左右就会折成两行、多占 20px。这类「说明文字」控制在 **50 字以内**比较稳。
- `p { margin: 0 }` 已在 base.css 重置，不需要额外去掉段间距。

## 十八、列比对为什么整页会出滚动条

症状：没选文件时页面很矮；A、B 都选好、结果出来以后，整页右侧多出一条纵向滚动条。

原因不在文件槽位，而在**结果列表撑到了固定的 `max-height: 330px`**。一屏里的固定开销本来就是：

```
顶栏 73 + 视口内边距 48 + 文件槽位 100 + 选项面板 122 + 状态 20 + 统计卡 60 + 标签页/工具条 70 + 底部说明 21 + 间距 60 ≈ 574
```

再加 330 的列表就是 900 上下，窗口一矮（或系统缩放 125%/150%）必然溢出。

修法不是继续抠像素，而是**让列表只吃剩余高度，并给它一个最高高度**：

```css
.tool-body.is-fill { height: 100%; min-height: 0; }      /* 高度=视口，正常窗口下页面不滚动 */
.tool-body.is-fill > .opt-panel, > .status, > .stats, > .hint { flex: none; }
.result-pane { display: contents; }                       /* 结果区不生成盒子，三个子块直接参与 body 布局 */
.tool-body.is-fill .data-list { flex: 0 1 auto; min-height: 70px; }  /* 上限仍用 .data-list 的 330px */
```

三个关键点：

1. **结果区不要包一层 flex 盒子**。包了就会踩坑：写 `min-height: 0` 能收缩，但缩到低于「标签页 + 工具条 + 最小列表」时子元素会溢出、压住下面的说明文字；不写 `min-height: 0`，`min-height: auto` 又等于内容高度，列表根本不缩（实测 20 行时整页直接多出 214px 滚动）。用 `display: contents` 让三个子块直接成为 `.tool-body` 的 flex 项，列表就成了唯一可收缩项，问题自然消失。
2. 列表用 `flex: 0 1 auto` + `min-height: 70px`：内容少时自然高度，内容多时压到剩余空间，最低留两行多。
3. **不做按窗口高度切换的“响应式 UI”**。统计卡始终是六张卡片、底部说明始终显示——用户明确要求这两块不要随窗口变形。窗口矮到放不下时（约 < 640px）宁可整页滚动：这是可接受的降级，元素之间绝不重叠。

实测（1180 宽，窗口高度 583/723；1600 宽，890 高）：583 高时列表 69px、页面滚动 62px 但说明不压列表；890 高时列表 275px、无整页滚动；两种情况统计卡都是卡片。

顺带把 `.split` 的断点从 1000px 改成 `repeat(auto-fit, minmax(330px, 1fr))`：文件槽位比文本域窄得多，1120px 窗口下没必要上下堆叠（一叠就多 104px）。

测试固化在 `test/e2e/column-compare-fit.js`：用两份 400 行的 fixture，断言 `view.scrollHeight <= view.clientHeight`、列表自身可滚、说明文字在列表下方；再真实缩放窗口验证矮窗口（卡片不变形、列表 ≥ 60px、说明不压列表）和大窗口（无整页滚动、列表 ≤ 330px）。小数据（5 行）测不出这个问题，fixture 必须够大。
